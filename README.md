# GoGlobal

Сервис сопровождения академического обмена. В системе есть три роли: студент-обменник, study-buddy и куратор.

## Технологии

- Python 3.12
- Django 6.0
- PostgreSQL 17
- Django templates и htmx
- Docker Compose для локального запуска

## Роли пользователей

- Вход выполняется по электронной почте.
- Поддерживаются роли `student`, `buddy` и `curator`.
- Для buddy и куратора доступ открывается после ручного одобрения.
- У каждой роли есть свой профиль.

## Локальный запуск через Docker Compose

Для запуска понадобятся Git и Docker Desktop.

1. Склонируйте репозиторий и перейдите в папку проекта.
2. Создайте локальный файл настроек:

   ```bash
   cp .env.example .env
   ```

3. Откройте `.env` и задайте `DJANGO_SECRET_KEY` и `POSTGRES_PASSWORD`. Не отправляйте этот файл в Git и не публикуйте секреты.
4. Соберите образы и запустите приложение с базой данных:

   ```bash
   docker compose up --build -d
   ```

5. Примените миграции:

   ```bash
   docker compose exec web python manage.py migrate
   ```

6. При необходимости создайте администратора:

   ```bash
   docker compose exec web python manage.py createsuperuser
   ```

7. Откройте приложение в браузере: <http://localhost:8000>

Данные базы хранятся в именованном томе `postgres_data` и переживают
остановку и перезапуск контейнеров. Том удаляется только командой
`docker compose down -v` — без флага `-v` данные на месте.

### Локальный почтовый приёмник (Mailpit)

В compose-файле есть сервис Mailpit — локальный SMTP-сервер с веб-интерфейсом,
чтобы видеть письма (коды подтверждения, восстановление пароля) не в консоли,
а в нормальном «почтовом ящике».

1. В `.env` переключите почту на SMTP:

   ```bash
   EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend
   EMAIL_HOST=127.0.0.1
   EMAIL_PORT=1025
   EMAIL_USE_TLS=0
   ```

2. Перезапустите приложение и откройте ящик: <http://127.0.0.1:8025>

## Проверка приложения

Посмотреть состояние контейнеров:

```bash
docker compose ps
```

Проверить конфигурацию Django:

```bash
docker compose exec web python manage.py check
```

Проверить, что миграции соответствуют моделям:

```bash
docker compose exec web python manage.py makemigrations --check --dry-run
```

Запустить тесты:

```bash
docker compose exec web python manage.py test
```

## Ручной запуск проверок CI

Если GitHub Actions недоступен, основные проверки можно выполнить вручную:

1. Запустите базу данных:

   ```bash
   docker compose up -d db
   ```

2. Проверьте конфигурацию Django:

   ```bash
   docker compose run --rm web python manage.py check
   ```

3. Проверьте миграции:

   ```bash
   docker compose run --rm web python manage.py makemigrations --check --dry-run
   ```

4. Запустите тесты:

   ```bash
   docker compose run --rm web python manage.py test
   ```

После изменения зависимостей пересоберите образ приложения:

```bash
docker compose build web
```

## Журнал событий

Технические сообщения приложения содержат идентификатор события. Секреты в сообщениях маскируются. Не добавляйте в журнал пароли, коды подтверждения и другие личные данные.

Команда ниже только показывает, сколько старых записей журнала можно удалить:

```bash
docker compose exec web python manage.py cleanup_audit_events
```

Чтобы выполнить удаление, добавьте флаг `--apply`:

```bash
docker compose exec web python manage.py cleanup_audit_events --apply
```

## Локальный запуск Django без Docker

В этом варианте приложение Django запускается прямо на компьютере, но база
данных PostgreSQL всё равно нужна — без неё `migrate` и `runserver` не
запустятся. Проще всего поднять базу в Docker-контейнере (шаг 4); если
PostgreSQL установлен на компьютере напрямую, шаг 4 можно пропустить.

1. Создайте и активируйте виртуальное окружение:

   ```bash
   python3.12 -m venv .venv
   source .venv/bin/activate
   ```

2. Установите зависимости:

   ```bash
   pip install -r requirements.txt
   ```

3. Создайте `.env` из примера и заполните нужные настройки:

   ```bash
   cp .env.example .env
   ```

4. Поднимите PostgreSQL в Docker. Данные сохраняются внутри контейнера,
   пока вы его не удалите:

   ```bash
   docker run --name goglobal-pg \
     -e POSTGRES_DB=goglobal -e POSTGRES_USER=goglobal \
     -e POSTGRES_PASSWORD=<тот же пароль, что в .env> \
     -p 5432:5432 -d postgres:17
   ```

   Если контейнер уже создан ранее, просто запустите его снова:

   ```bash
   docker start goglobal-pg
   ```

5. Примените миграции и запустите сервер:

   ```bash
   python manage.py migrate
   python manage.py runserver
   ```

6. Откройте <http://127.0.0.1:8000>.

## D04-3. Ручной выпуск версии

Эта инструкция задаёт общий порядок ручного выпуска GoGlobal после успешного CI. Команды запуска на сервере зависят от выбранной площадки и будут добавлены после её выбора.

### Перед выпуском

1. Убедитесь, что нужный коммит отправлен в GitHub и для него CI завершился успешно.
2. Запишите короткий идентификатор коммита, который выпускаете. Не используйте плавающую версию вроде `latest`.
3. Убедитесь, что для среды подготовлены отдельные значения настроек. Секретный ключ Django, пароль базы данных и SMTP-пароль храните в секретах среды или в локальном `.env`, который не попадает в Git.
4. Перед изменениями базы данных создайте резервную копию и проверьте, что файл копии создан и имеет ненулевой размер.

### Выпуск

1. Получите на стенде именно проверенный коммит или его версионный тег.
2. Соберите приложение из этого коммита.
3. Примените миграции базы данных предусмотренной для стенда командой.
4. Запустите или перезапустите приложение.
5. Проверьте доступность приложения, выполните проверку Django и просмотрите журналы на ошибки.
6. Запишите в журнал выпуска идентификатор коммита, дату, результат CI, результат миграций и результат проверки после запуска. Не записывайте секреты и персональные данные.

### Если выпуск не удался

1. Зафиксируйте ошибку и идентификатор коммита.
2. Если ошибка только в приложении, верните предыдущую проверенную версию кода.
3. Не откатывайте миграции базы данных вслепую: откат кода сам по себе не отменяет изменения схемы. При проблеме с данными остановите выпуск и восстановите базу из проверенной резервной копии либо подготовьте исправляющую миграцию.
4. После исправления повторите выпуск с новым коммитом и успешным CI.

### Ограничения текущей инструкции

Площадка для стенда ещё не выбрана. Поэтому здесь не указаны адрес сервера, способ доставки образа, команды управления сервисом и место хранения резервных копий. Их нужно заполнить после выбора площадки.

Текущий локальный `docker-compose.yml` запускает Django через `runserver`, предназначенный для разработки. Сам по себе этот файл не является готовой публичной production-конфигурацией.
